# 일일 업무일지 작성

하루치 업무 내용을 읽어 붙임1 일일 업무일지 양식을 채운다.

**역할 분담이 이 시스템의 핵심이다.** 문서 생성(`fill_hwpx.py`)은 결정론적이므로 스크립트가
하고, 분류·요약·문체는 판단이라 네가 한다. 이 경계를 넘지 마라 — 셀 좌표를 직접 만지거나
hwpx XML을 손으로 편집하지 말고, 반대로 건수 집계를 스크립트에 떠넘기지도 마라.

입력원은 세 가지이고 초안 JSON 스키마는 어느 쪽이든 같다. 2단계부터는 입력원을 구분하지 않는다.

## 인자

- `--date YYYY-MM-DD` — 대상 날짜 (기본: 오늘)
- `--draft` — 3단계까지만 하고 멈춘다. 스케줄러가 밤에 초안만 만들어 둘 때 쓴다.
- `--yes` — 4단계(확인)를 건너뛰고 HWPX까지 만든다. `Codex -p` 비대화형 실행용.
  `--draft`와 같이 주면 `--draft`가 이긴다.
- `--discord` — 디스코드에서 로그를 수집한다. 봇 권한이 잡혀 있을 때만 쓴다.
- `--notes <경로>` — 메모 파일 경로를 직접 지정한다 (기본: `notes/<날짜>.md`)
- `--redraft` — 이미 있는 `drafts/<날짜>.json`을 버리고 입력에서 초안을 다시 만든다.
- `--no-upload` — 드라이브 업로드를 건너뛰고 로컬 `out/`까지만 만든다.
- `--folder <URL 또는 ID>` — 이번 한 번만 다른 드라이브 폴더에 올린다.
  기본 대상은 `config.toml`의 `[drive]`에서 읽는다.

## 절차

### 1. 입력 확보

#### 먼저 — 이미 만들어 둔 초안이 있는가

**`drafts/<날짜>.json`이 이미 있으면 입력 확보와 2단계를 건너뛰고 그 파일을 읽어 3단계부터
이어간다.** `--draft`로 만들어 둔 초안을 사용자가 손으로 고쳤을 수 있는데, 다시 만들면 그
수정이 말없이 사라진다. 스케줄러가 초안을 만들어 두고 사람이 확인해 확정하는 흐름 자체가
이 규칙에 걸려 있다.

예외는 셋뿐이다. 어느 쪽도 아니면 초안을 다시 만들지 마라.

- `--redraft`가 있다
- `--discord`가 있다 — 새로 수집하라는 뜻이다
- 프롬프트나 stdin에 새 업무 내용이 실려 왔다 — 다시 쓰라는 뜻이다

초안을 버리고 다시 만들 때는 그렇게 하고 있다고 한 줄로 알려라.

#### 초안이 없으면 — 입력원을 찾는다

이 순서로 결정한다. 위에서 걸리면 아래는 보지 않는다.

1. **`--discord`가 있으면** → 디스코드에서 수집한다

   ```bash
   python3 tools/fetch_discord.py --date <날짜> --out logs/<날짜>.json
   ```

   0건이면 멈추고 사용자에게 알려라. MESSAGE CONTENT INTENT가 꺼졌거나 채널 권한이
   없는 경우가 대부분이다. 없는 하루를 지어내지 마라.

2. **프롬프트나 stdin에 하루 내용이 이미 실려 있으면** → 그걸 입력으로 쓴다

   ```bash
   echo "김OO git 오류 답변, 이OO 미접속 DM" | Codex -p "/daily-log --yes"
   Codex -p "/daily-log --yes 오늘 문의 2건 응대했고 시설 이상 없었음"
   ```

   플래그를 뺀 나머지 텍스트가 그날의 업무 내용이면 그것이 입력이다. 파일을 찾지 말고
   바로 2단계로 간다. 다만 **묻지 않고 넘어가는 만큼 지어내지도 마라** — 모호한 항목은
   분류하지 말고 빼는 편이 낫다.

3. **`notes/<날짜>.md`가 있으면** → 그 파일을 읽는다

   자유 서식이다. 형식을 요구하지 말고 내용만 읽어내라. 다만 **분류할 수 없을 만큼 모호하면
   초안을 쓰기 전에 물어봐라** — 몇 명에게 안내한 건지, 문의에 답한 건지 학습 방법을 지도한
   건지 판별이 안 될 때다. 추측으로 메우지 마라. (`--yes`면 물어볼 수 없으니 그 항목을 뺀다.)

4. **아무것도 없으면** → 대화로 물어본다

   아래를 한 번에 제시하고 자유롭게 답하게 한다. 항목별로 나눠 캐묻지 마라 — 사용자가 한
   덩어리로 답하면 그걸 분류하는 게 네 일이다.

   ```
   <날짜> 일지를 만듭니다. 오늘 있었던 일을 편하게 적어주세요.
     - 교육생 문의와 어떻게 답했는지
     - 상담·참여 독려한 일
     - 학습 방법이나 미션 진행을 지도한 일
     - 운영팀에 전달할 것 (시설, 이탈 징후, 인수인계)
   기억나는 것만 적으셔도 됩니다.
   ```

   **`--yes`인데 여기까지 왔으면 묻지 말고 에러로 멈춰라.** 비대화형이라 답할 사람이 없다.
   "입력이 없습니다 — stdin·인자·`notes/<날짜>.md` 중 하나가 필요합니다"라고 알리고 끝낸다.
   없는 하루를 지어내느니 실패하는 게 낫다.

#### 입력 원문 보존

2번·4번으로 받은 원문은 **그대로 `notes/<날짜>.md`에 저장한다.** 요약해서 저장하지 마라.
나중에 분류를 고치거나 초안을 다시 만들 때 근거가 남고, 대화가 날아가도 복구된다.
3번은 이미 그 파일이 원본이므로 덮어쓰지 않는다.

#### author / team 확보

초안 JSON의 필수 값이라 입력원과 무관하게 필요하다. `config.toml`에서 읽되, 파일이 없으면
사용자에게 이름과 조를 한 번 묻고 `config.example.toml`을 바탕으로 `config.toml`을 만들어
저장한다. 매일 다시 묻지 않기 위해서다.

### 2. 판단 — 분류·집계·작성

`style/guide.md`를 먼저 읽어라. 그게 문체의 기준이고, 누적 규칙이 기준선보다 우선한다.

입력을 읽고 세 갈래로 나눈다. **분류 단위는 메시지가 아니라 "사안"이다.** 한 사안을 두고
메시지가 열 번 오갔어도 1건이다.

| 분류 | 무엇인가 | 판별 기준 |
|---|---|---|
| `first_response` (1차 응대) | 교육생 문의에 답해 해결한 것 | 질문이 있고 답이 있었나 |
| `learning_support` (학습 지원) | 상담, 참여 독려, 이탈 방지 | 학습 자체보다 사람의 상태를 다뤘나 |
| `guidance` (가이드) | 미션 수행·학습 방법 지도 | 어떻게 학습할지를 알려줬나 |

경계가 모호하면 교육생이 무엇을 얻어갔는지로 판단한다. 답을 얻었으면 1차 응대,
마음이 움직였으면 학습 지원, 방법을 배웠으면 가이드다.

그다음 초안 JSON을 만들어 `drafts/<날짜>.json`에 쓴다:

```json
{
  "date": "2026-07-30",
  "author": "config.toml의 author",
  "team": "config.toml의 team",
  "summary": "한 문장. 마침표 하나.",
  "operation_note": "교육장 상주·환경 점검 특이사항. 없으면 빈 문자열.",
  "counts": { "first_response": 3, "learning_support": 2, "guidance": 1 },
  "inquiry_lines": ["[문의 1] ...", "조치 내용: ..."],
  "counseling_lines": ["[상담 내용 1] ...", "[참여 독려 1] ..."],
  "guidance_lines": ["[학습 지도 1] ...", "가이드 내용: ..."],
  "handover_lines": ["운영팀 전달 및 건의사항. 시설 보수, 이탈 징후, 인수인계."]
}
```

`counts`의 숫자는 상세 항목 수와 일치해야 한다. 어긋나면 둘 중 하나가 틀린 것이다.
해당 내역이 없는 칸은 빈 배열로 두면 스크립트가 `해당 없음`을 넣는다.

#### 분량 제한 — 셀 높이가 고정이다

양식은 셀 높이가 정해져 있어서 넘치면 표가 아래로 밀리고 한 장짜리 서식이 깨진다.
**한 줄은 한글 49자**이고(영숫자는 절반), 그보다 길면 자동으로 다음 줄로 넘어가 두 줄을 먹는다.

| 항목 | 최대 줄 수 | 실질 |
|---|---|---|
| `summary` | **1줄** | 한글 49자. 가장 빡빡하다 |
| `inquiry_lines` | 7줄 | 문의 3~4건 (건당 2줄) |
| `counseling_lines` | 7줄 | 상담·독려 합쳐 3~4건 |
| `guidance_lines` | 7줄 | 학습지도 3건 |
| `handover_lines` | 9줄 | |
| `team` | 2줄 | |
| `operation_note` | 3줄 | |

건수가 많아 다 못 담으면 **항목을 지우지 말고 묶어라.** 비슷한 문의는 한 항목으로 합치고
`(유사 문의 3건)`처럼 덧붙인다. `counts`의 숫자는 실제 건수 그대로 두고 줄이지 않는다.

`verify_hwpx.py`가 초과를 잡아내며, 몇 줄을 줄여야 하는지 알려준다.

### 3. 초안 제시

초안을 표 형태로 화면에 보여준다. 파일 경로만 알려주고 끝내지 마라 — 사용자가 읽고
고칠 수 있어야 이 단계에 의미가 있다. 건수와 상세 항목 수가 맞는지도 같이 보여준다.

`--draft`면 여기서 멈추고 "확인 후 `/daily-log`로 확정하세요"라고 안내한다.
`--yes`면 표는 보여주되 승인을 기다리지 말고 5단계로 간다.

### 4. 확인과 수정

**`--yes`면 이 단계를 건너뛴다.** 그 외에는 건너뛰지 않는다.

사용자가 고쳐달라고 하면 `drafts/<날짜>.json`을 고치고 다시 보여준다. 승인할 때까지 반복한다.

### 5. HWPX 생성과 제출

```bash
python3 tools/fill_hwpx.py --in drafts/<날짜>.json
python3 tools/verify_hwpx.py "<위에서 출력된 경로>" --against drafts/<날짜>.json
python3 tools/upload_drive.py "<같은 경로>"
```

**`--out`을 주지 마라.** 제출용 파일명(`[코디세이]MMDD(요일)_<이름>_퍼실리테이터 일일업무일지.hwpx`)은
운영팀이 요구하는 형식이라 `fill_hwpx.py`가 초안의 날짜·이름에서 직접 만든다. 파일명을 손으로
조립하면 요일이 틀어진다. `fill_hwpx.py`가 출력한 경로를 그대로 다음 명령에 넘겨라.

검사가 실패하면 초안을 고쳐 다시 만든다. 실패한 채로 사용자에게 넘기지 마라.
**`--yes`여도 이 검사는 건너뛰지 않는다.** 다만 **재시도는 2회까지다.** 같은 실패를 계속
붙들고 있지 말고, 두 번 고쳐도 통과하지 못하면 멈추고 검사기가 뭐라고 했는지 그대로 알린다.

#### 드라이브 업로드

`upload_drive.py`는 `config.toml`의 `[drive]`에서 제출 폴더를 읽어 rclone으로 올린다.
**폴더 주소를 네가 조립하거나 명령에 적어 넣지 마라.** 폴더가 바뀌면 사용자가 설정을 고친다.
`--folder`를 사용자가 준 경우에만 그대로 넘긴다.

- **검사를 통과한 뒤에만 올린다.** 반려될 파일을 운영팀 폴더에 올리지 마라.
- `--no-upload`가 있으면 이 단계를 건너뛴다.
- 스크립트가 "업로드 건너뜀 ([drive] 미설정)"이라고 하면 **실패가 아니다.** 드라이브 설정을
  안 한 것뿐이니 건너뛰었다고만 알리고 끝낸다. 설정하라고 재촉하지 마라.
- 업로드가 실패하면 **그 작업은 실패다.** 파일은 만들어졌으니 로컬 경로는 알려주되, 제출이
  안 됐다는 것과 스크립트가 알려준 원인을 분명히 말한다. 성공한 것처럼 마무리하지 마라.
- 성공하면 스크립트가 출력한 드라이브 링크를 사용자에게 보여준다.

#### 출력

`--yes`일 때는 **마지막 줄에 생성된 로컬 파일 경로만 단독으로 출력한다.** 드라이브 링크가
아니라 파일 경로다. 설명을 덧붙이지 마라 —
`OUT=$(Codex -p "/daily-log --yes" | tail -1)`로 스크립트가 받아쓸 수 있어야 한다.
드라이브 링크는 그보다 앞줄에 남기면 된다.

### 6. 문체 학습

사용자가 4단계에서 문장을 고쳤다면, 그 교정의 **방향**을 규칙으로 뽑아 `style/guide.md`의
"누적 규칙"에 날짜와 함께 추가한다. 고친 문장 자체를 옮겨 적는 게 아니라 다음부터 적용할
규칙으로 일반화해야 한다.

교정이 없었으면 아무것도 추가하지 마라. 규칙이 늘어나는 게 목적이 아니라 다음 초안의
수정량이 줄어드는 게 목적이다.

## 하지 말 것

- 입력(메모·대화·로그)에 근거가 없는 내용을 채워 넣기 — 빈칸이 지어낸 문장보다 낫다
- 메모가 짧다고 살을 붙여 부풀리기 — 3건이면 3건짜리 일지가 맞다
- 건수를 보기 좋게 맞추기
- `verify_hwpx.py` 실패를 무시하고 넘어가기 — `--yes`는 확인을 건너뛰는 것이지 검사를
  건너뛰는 게 아니다
- 사용자 확인 없이 최종 파일을 만들기 (`--yes`가 없으면 `--draft`가 아니어도 4단계는
  건너뛰지 않는다)
- `--yes`인데 입력이 없다고 하루를 지어내기 — 멈추고 알려라
- 이미 있는 `drafts/<날짜>.json`을 말없이 새로 만들어 덮어쓰기 — 사람이 고쳐 둔 것일 수 있다
- 검사에 실패한 파일을 드라이브에 올리기
- 업로드가 실패했는데 파일 경로만 보여주고 끝내기 — 제출이 안 된 것이다
